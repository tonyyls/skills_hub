## 目标
- 使用 Supabase/Postgres 物化视图预聚合分类计数，显著降低 `/api/skills/category-counts` 响应时间。
- 在服务端增加内存缓存 + ETag + CDN 缓存头，进一步减少重复查询与传输。

## 变更内容
1) 数据库迁移
- 新增迁移：`supabase/migrations/20251117_category_skill_counts_mv.sql`
- 创建物化视图与索引：
```sql
DROP MATERIALIZED VIEW IF EXISTS public.category_skill_counts_mv;
CREATE MATERIALIZED VIEW public.category_skill_counts_mv AS
SELECT category_id, COUNT(*) AS count
FROM public.skills
WHERE status = 'published'
GROUP BY category_id;
CREATE INDEX IF NOT EXISTS idx_category_skill_counts_mv_category_id
ON public.category_skill_counts_mv (category_id);
```

2) 后端路由优化
- 文件：`api/routes/public.ts`
- 添加进程内缓存（TTL 10 分钟）与 ETag 计算函数。
- 修改 `GET /api/skills/category-counts`：
  - 先读内存缓存并返回（命中时支持 If-None-Match → 304）
  - 未命中则查询：
    - `categories`（启用）与 `category_skill_counts_mv`（聚合计数）
    - 合并结果、回填缓存、设置 `Cache-Control: s-maxage=600, stale-while-revalidate=86400` 与 `ETag`
  - 若视图不存在或查询失败，降级为当前循环计数逻辑

3) 前端无需改动
- 现有 `fetchCategoryCounts()` 调用的 `/api/skills/category-counts` 自动受益。

## 验证
- 本地启动后访问 `/api/skills/category-counts`，首次命中视图查询；后续命中内存缓存或返回 304。
- 观察响应时间与 Network 请求体积减少。

## 后续（可选）
- 增加管理端刷新端点或使用 Supabase 定时任务执行：`REFRESH MATERIALIZED VIEW CONCURRENTLY public.category_skill_counts_mv;` 每 5–10 分钟。

## 风险与回滚
- 若视图创建失败或影响查询，路由内置降级到原计数逻辑。
- 迁移可回滚：`DROP MATERIALIZED VIEW public.category_skill_counts_mv;`
