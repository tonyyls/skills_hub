## 问题与目标
- 问题：`/categories` 与 `category-counts` 接口返回较慢，影响首页与列表的首屏体验。
- 目标：在不改变功能与数据一致性的前提下，降低接口响应时间、减少重复查询。

## 推荐组合方案（服务端优先）
- 服务端内存缓存（TTL 5–10 分钟）+ CDN 缓存（s-maxage + stale-while-revalidate），覆盖 80% 访问场景。
- 类目计数采用数据库侧加速：物化视图或增量计数表（触发器维护），保障查询常量时间。
- ETag/If-None-Match 配合前端条件请求，避免重复传输。

## 方案 A：服务端内存缓存 + CDN 缓存
- 在 `GET /api/categories` 与 `GET /api/skills/category-counts` 路由加入：
  - 进程内缓存 Map（key=查询参数，value={data, expiresAt}）
  - 命中缓存直接返回；未命中拉 Supabase，回填缓存
  - 设置响应头：`Cache-Control: s-maxage=600, stale-while-revalidate=86400`
  - 生成 ETag（如 `sha1(JSON.stringify(data))`）并支持 If-None-Match 返回 304
- 优点：实现简单，立即见效；在 Vercel/前置 CDN 环境下命中率高。
- 注意：Serverless 进程重启会失效；可结合 KV/Redis 提升稳健性。

### 示例（Node/Express 伪代码）
```ts
/**
 * @function getCached
 * @description 读取内存缓存，过期返回 null。
 */
function getCached<T>(key: string): T | null { /* ... */ }

/**
 * @function setCached
 * @description 写入内存缓存并设置 TTL。
 */
function setCached<T>(key: string, value: T, ttlMs = 600000): void { /* ... */ }

/**
 * @function etagOf
 * @description 计算数据 ETag，用于条件请求。
 */
function etagOf(obj: unknown): string { /* sha1(JSON.stringify(obj)) */ }

app.get('/api/categories', async (req, res) => {
  const key = 'categories:active'
  const cached = getCached(key)
  if (cached) {
    const etag = etagOf(cached)
    if (req.headers['if-none-match'] === etag) return res.status(304).end()
    return res.set('ETag', etag).set('Cache-Control', 's-maxage=600, stale-while-revalidate=86400').json(cached)
  }
  const { data } = await supabase.from('categories').select('id,name').eq('is_active', true)
  setCached(key, data, 600000)
  res.set('ETag', etagOf(data)).set('Cache-Control', 's-maxage=600, stale-while-revalidate=86400').json(data)
})
```

## 方案 B：数据库侧加速（物化视图/增量计数）
- 物化视图（推荐）：
  - 建视图 `category_skill_counts_mv`：
    ```sql
    CREATE MATERIALIZED VIEW category_skill_counts_mv AS
    SELECT category_id, COUNT(*) AS count
    FROM skills
    WHERE status='published'
    GROUP BY category_id;
    ```
  - 并发刷新：`REFRESH MATERIALIZED VIEW CONCURRENTLY category_skill_counts_mv;`
  - 通过 Supabase 任务或外部 Cron 每 5–10 分钟刷新一次
  - 路由查询改为视图：`SELECT c.id, c.name, COALESCE(mv.count,0) FROM categories c LEFT JOIN category_skill_counts_mv mv ON mv.category_id=c.id WHERE c.is_active=true`
- 增量计数表（实时）：
  - 维护 `category_counts(category_id,count)`，由触发器在 `skills` 的 `INSERT/UPDATE(status/category_id)/DELETE` 时增减
  - 优点：实时、查询 O(1)；缺点：实现复杂、需谨慎处理并发与回滚

## 方案 C：ETag/条件请求与前端 SWR
- 服务端：如方案 A 添加 ETag 与 304 支持
- 前端：调用时带 `If-None-Match`，命中返回 304，使用本地缓存；或使用 SWR 模式（stale-while-revalidate）
- Pinia 层：缓存 `categories` 与 `categoryCounts`，加 `updatedAt` 与最小刷新间隔（如 10 分钟），避免页面间重复拉取

## 方案 D：边缘/持久缓存
- KV/Redis：将 `categories` 与 `category-counts` 存入 KV（Vercel KV / Redis），TTL 10–30 分钟
- Supabase Edge Functions 或 Vercel Edge Functions：在边缘聚合与缓存响应（适合全球用户）

## 接入建议与步骤
1. 先落地方案 A（内存 + CDN + ETag），改动最小、收益显著
2. 对 `category-counts` 接口引入物化视图（方案 B），显著降低查询成本
3. 前端 Pinia 加 TTL 与去重，页面初始化只拉一次（已有 ensureCategoriesLoaded，可加时间窗）
4. 如有全球流量与更高稳定性要求，再接入 KV/Redis（方案 D）

## 风险与回滚
- 缓存时效导致“新增分类/变更计数”短时未同步：通过 TTL 与手动刷新路由（管理端变更后清缓存）规避
- 物化视图刷新失败：保留原查询作为降级路径；监控刷新任务并报警

## 验收点
- 分类与计数接口 P50 响应时间显著降低
- 首页首屏 pending 明显减少；重复导航命中缓存（304 或 CDN）
- 数据一致性在 TTL 窗口内满足预期（≤10 分钟）

## 后续拓展
- 管理端变更（新增/删除分类、发布技能）后触发清缓存（简单 webhook 或后端接口）
- 前端预渲染/静态化分类列表（如在构建期写入 JSON 并在运行时用缓存校验）
